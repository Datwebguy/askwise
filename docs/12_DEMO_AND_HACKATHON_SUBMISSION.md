# 12. DEMO AND HACKATHON SUBMISSION

## 1. What the demo must prove

Show a real AskWise workflow.

The judge should understand:
- What problem AskWise solves.
- How someone uses it.
- How it researches information.
- How it compares products.
- What appears on the glasses.
- What appears on the phone.
- How Notion works.
- How the user approves an action.

## 2. Three-minute demo plan

### 0:00 to 0:20
Explain the problem.

People spend too much time searching different websites and comparing conflicting information.

### 0:20 to 0:45
Ask AskWise to compare products based on specific needs.

### 0:45 to 1:25
Show the research process.

Show how AskWise identifies exact models and collects information.

### 1:25 to 1:55
Show the glasses result.

Explain the recommendation and its main disadvantage.

### 1:55 to 2:25
Show the phone report.

Show:
- Comparison table.
- Specifications.
- Prices.
- Sources.
- One checked claim.
- One disagreement or missing detail.

### 2:25 to 2:50
Show Notion.

Preview the report, approve it and show the saved page.

### 2:50 to 3:00
Close with a simple explanation of AskWise's value.

## 3. Prepare before recording

Prepare:
- A stable demo account.
- A Notion test workspace.
- A product comparison question.
- A general research question.
- Reliable public sources.
- Working G2 simulator.
- Working phone interface.
- Backup demo data.

If you use results collected earlier, label them as prepared demo data.

Do not pretend old results are live research.

## 4. Recording

The agent's sandbox cannot run the official simulator.

The product owner must record the demo on their own computer or on a physical G2 device.

The hackathon accepts simulator recordings.

## 5. README requirements

The GitHub README must explain:

- Product name.
- One-line description.
- Problem.
- Target users.
- How AskWise works.
- Main features.
- Product research example.
- General research example.
- Why G2 is useful.
- System architecture.
- Notion integration.
- Permissions.
- Setup instructions.
- Required environment variable names.
- Simulator instructions.
- Screenshots.
- Demo video.
- Known limitations.
- Privacy and security.
- Team information.

It must explain what existed before November 23.

## 6. Hackathon project description

Explain:
- The problem.
- Who AskWise helps.
- How it works.
- Why it uses G2.
- The selected track.

Use simple language.

## 7. Submission checklist

- Public GitHub or GitLab repository.
- Complete README.
- Demo video of up to 3 minutes.
- Short project description.
- Correct track selected.
- No private API keys in the repository.
- Financial features remain within the hackathon safety rules.
- Submission completed before the deadline.

Official deadline recorded: November 29, 23:59 Dubai time.

Submit with enough time for technical problems.

## 8. Be honest about the product

Never claim:
- A feature works when it is only a mockup.
- An integration is complete when it is not.
- A source was checked when it was not.
- A product is unique without competitor research.
- The organisers approved something without confirmation.

Show what works. Clearly identify what remains planned.
